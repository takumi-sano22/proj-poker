# ui-design-recipes — UI デザインの実装レシピ集

Claude Code の skill として使う、UI デザインの実装値と作法の集まり。**人が読むための案内**はこのファイルに、
Claude が読むための導線は `../SKILL.md` にある。

## これは何か

- 確立したデザイン体系を、**実装の値の単位で再現する**ためのレシピ集。色の使い方、面の重なりと影、文字・余白・角丸、
  動き、コントラスト、部品、配置、演出を扱う。
- 美学の方向性を 0 から決めるものではない。方向性が決まった後（または本レシピの体系を採用すると決めた後）に、
  毎回同じ品質で作るためのもの。
- **色は HEX 値を持たない。** 色そのものはプロジェクトのベースライン色で決まるので、役割・濃淡の段・
  グラデーションのかけ方・アクセントの散らし方という「使い方」だけを書いてある。
- **形（角丸・影・余白・幅・高さ・所要時間）は値そのまま**書いてある。そのまま写してよい。
- 書式は Tailwind v4 のクラスと、素の CSS 値の併記。Tailwind を使わないプロジェクトでも読み替えられる。

## Claude Code での使われ方

1. UI の作業を頼むと、skill の description にある語でこの skill が選ばれる。
2. Claude は `SKILL.md` の対応表を見て、作るものに対応する reference **だけ**を読む
   （全部を読むとコンテキストを浪費するため、SKILL.md には知見を書いていない）。
3. プロジェクトに固有補強 md があれば、reference より先に読む（下記）。

## 他のプロジェクトに導入する

1. **skill を置く。** 全プロジェクトで使うなら `~/.claude/skills/ui-design-recipes/`、
   1 つのリポジトリだけなら `<repo>/.claude/skills/ui-design-recipes/` にディレクトリごとコピーする。
   - 同じ名前の skill を両方に置くと、Skill ツールは global 版（`~/.claude/skills`）を読む（Claude Code の挙動として 2026-08 に確認）。
     **プロジェクト固有の内容は skill ディレクトリの相対参照だけに頼らず**、`CLAUDE.md` から repo のパスで指す。
2. **ベースライン色を決める。** `foundations/color-usage.md` §4 の手順で、アンカー 2 色（主ボタン＝600・リング＝500）、
   隣接色相の accent、本文色の色相に寄せたニュートラル（ink）を決め、50〜900 の段を作る。
3. **トークンを置く。** foundations の各 reference にあるトークン定義のコード（`@theme` の雛形）を、グローバル CSS
   （Tailwind v4 なら `@theme static`、それ以外なら `:root`）へ写し、値を埋める。
4. **コントラストの表を作る。** `foundations/contrast-and-a11y.md` の計算で、主要な組み合わせ
   （本文・補助文字・輪郭・白文字の塗り・グラデーションの端）を測り、プロジェクトの設計書に残す。割れた段は値を調整する。
5. **固有補強 md を作り、`CLAUDE.md` から指す。** 次節のテンプレートを使う。
6. 画面・部品を作るときは、SKILL.md の対応表から reference を選んで Claude に作業させる。

## 固有補強 md の作り方

プロジェクトごとの事情（実際の色の値・既存部品・禁止事項）は reference に書かず、
**1 枚の md** にまとめて `CLAUDE.md` から指す。Claude は reference より先にこれを読む。

置き場所の例: `<repo>/.claude/skills/ui-design-recipes/<project>.md`（global 版には置かない）。
`.claude/rules/<UI 領域>.md`（UI 方針。対象パスに触れたときだけ読まれる rule）には「UI を作る・直すときは `ui-design-recipes` skill の前に `<path>` を読む」と書く。

```markdown
# ui-design-recipes: <プロジェクト名> 固有の補強

## 位置づけと優先順位
実装（トークンを定義した CSS・共通部品）＞ 本 md ＞ 汎用の reference。
reference と違うところは、このプロジェクトの例外として本 md に書く（reference は他のプロジェクトと共有しているので、
書き換えるのは一般則そのものが誤っている／改善されたときだけにする）。

## 当てはめ例（実際の値）
アンカー色・専用色相・影の色など、reference が役割名で書いているものの実際の値。

## 既存部品の対応表
| 作るもの | 使う実装（新しく作らない） |

## このプロジェクト固有の規律・例外
倫理・ブランド・プロダクト上の禁止事項（例: 本人に危険色を向けない）と、reference からの例外。

## 関連 skill への導線
挙動・構造・コピーなど、このプロジェクトの他の skill の担当範囲。

## 出典の対応表
| reference | このプロジェクトでの出典（ファイル・設計書の節） |

## 既知のずれ
設計書と実装の食い違い・未対応事項と、その Issue。
```

## reference の型（追加・改訂するとき）

```markdown
# <タイトル>

> **いつ読むか**: <作るもの・状況>
> **前提**: <先に読む reference>
> <値の扱い（例: 形の値はそのまま再現してよい）>

## 目次          ← 300 行を超える場合は必須
## 1. 要点       ← 結論を 3〜6 行
## 2. …          ← 本体。表（役割 | 値 | Tailwind | 素の CSS | なぜ）と最小のコード
## 落とし穴
## チェックリスト
```

## 更新ルール

- **色は HEX 値を書かない**（白 `#fff` と透明を除く）。役割・段・相対関係（「白文字を載せる塗りは 4.5:1 以上の段」）で書く。
- **形・時間の値はそのまま書く。** 変えたら、抽出元の実装と突き合わせる（出典の対応は各プロジェクトの固有補強 md にある）。
- **汎用の reference にプロジェクト固有のパス・Issue 番号・固有名詞を書かない。** WHY は一般化して書く
  （例: 「青だと埋もれた」ではなく「ブランドや隣の面と同系色の発光は埋もれる」）。
- reference を足したら、`SKILL.md` の対応表とこの README の「構成」を同時に更新する。対応表に載っていない reference は読まれない。
- 1 本が 300 行を超えたら目次を付けるか、分ける。
- SKILL.md は 500 行以内。description は全セッションで読み込まれるので短く保ち、何の skill か・いつ使うか・frontend-design との優先順位だけを書く（トリガー語や発話例を並べない）。frontmatter を壊すと無言で
  description が消えるので、編集後は `claude plugin validate <skills ディレクトリ>` で確かめる。
- project と global の両方に置いている場合は、両方に同じ変更を当て、`diff -rq` で固有補強 md 以外に差が無いことを確かめる。
