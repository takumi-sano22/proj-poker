# 画面の見本（模式図）と注釈

> **いつ読むか**: 使い方の説明・オンボーディングなど「この画面のここの話です」を示す模式図を作るとき／模式図に注釈（枠・タグ・凡例）を付けるとき
> **前提**: `foundations/surface-and-depth.md` §5（面のレシピ 4 層・「層の外: 見本」の行）・`foundations/contrast-and-a11y.md`（コントラストの計算）
> 形の値（角丸・枠の太さ・サイズの目安）はそのまま再現してよい。専用色相そのものはプロジェクトの色から選ぶ。

## 1. 要点

- 見本は L1〜L4 のどの層にも属さない**層の外**の面（`foundations/surface-and-depth.md` §5「層の外: 見本」）。角丸 4px・強めの枠・白（最前面の面）・影なしで、隣に並ぶ説明カードとはっきり段差を付ける。
- 見本は実際のスクリーンショットではなく、**本体と同じ色・角丸・影のトークンで組んだ DOM** で描く。画像と違い、トークンの値が変わっても撮り直さずに追従する。
- 見本の中身は実物のコンポーネントをそのまま埋め込むのではなく、**縮小した専用のコピー**を書く。実寸を再現する必要はなく、「どこの話をしているか」が伝われば足りる。
- 注釈は「枠で要素を包む」か「タグだけを乗せる」かを図の大きさで使い分ける。**唯一の情報源は凡例（実テキスト）** にし、図とタグ自体は視覚的な飾りとして隠す。
- デスクトップ用とモバイル用の 2 種類を用意し、幅を JS 側の判定で出し分ける。中間の幅で実画面と見本の対応が崩れる場合は、図を増やさず 1 行の注記で補う。

## 2. 見本はどの層にも属さない

見本の面は既存の面のレシピ（`foundations/surface-and-depth.md`）のどれにも当てはめない。理由は、見本は「読む対象」でも「操作対象」でもなく、あくまで説明のための絵だから。L1〜L4 のどれかに寄せると、絵のはずが操作要素や読む対象に見えてしまう。

- **角丸は最小の段**（4px）にする。0px だと紙を切り抜いたように硬すぎるが、隣接する説明カード（脇役の面・12px）よりは明確に締める。
- **枠は隣の説明カードより強い段**にする。説明カードの枠が通常の強さなら、見本の枠は強めの段にして、テキストの塊（カード）と絵（見本）を一目で見分けられるようにする。
- **影は付けない。** 影を付けると「浮いた操作要素」に見えてしまい、層の外という位置づけと矛盾する。
- 面は最前面と同じ明るさ（白）にする。中に置く模倣コンポーネント自身の配色は上書きしない（実物の色をそのまま再現するのが目的のため）。

```
rounded-frame border border-border-strong bg-surface-raised p-3
```

**段差の作り方**: 見本と隣接カードは「角丸」と「枠の強さ」の 2 軸で同時にずらす。1 軸だけ変えても、もう 1 軸が同じだと近い見た目になり、「これは絵です」という区別が伝わりにくい。

## 3. DOM で描く理由・実物流用か縮小コピーか

- **画像（スクリーンショット）にしない。** 本体の実装・表示モード（不透明な面/背景を透かす面 等）・配色テーマが変わるたびに撮り直しが必要になり、すぐに実物と乖離する。デザイントークンを使った DOM で組めば、トークンの値が変わったときは自動で追従する。ただし「表示モードの違い」までは自動で追従しない作り方もあり得るので、その場合は模式図が固定でどちらのモードを表しているかをコメントで明記しておく。
- **実物のコンポーネントをそのまま import して埋め込まない。** 縮小した専用のコピーとして書く。理由は 2 つ:
  1. 見本は「絵」であって操作できてはいけない。実物にはクリックハンドラやフォーカス移動が付いているため、そのまま埋め込むと操作できる要素になってしまう。
  2. 見本が別レイヤー（モーダル等・フォーカストラップを持つ面）の中に置かれる場合、`button` / `a[href]` / `tabindex` を持つ要素が紛れ込むと、トラップ側の「フォーカス可能な要素」の走査に混入し、初期フォーカスやフォーカス順が壊れる。
- 縮小コピーは `div` / `span` だけで組み、操作用の属性は一切持たせない。コンポーネントの冒頭に「何を模しているか（対応する本体側の要素）」を一言添えておくと、本体の実装が変わって見た目がズレたときに気づける。
- 縮小コピーであっても、実物で「濃い色の塗りを許された要素（主操作・自分の発言 等)」を再現する場合はその色をそのまま使ってよい。見本は装飾ではなく実物の再現が目的なので、面のレシピの色数の上限規律の対象外として扱う。

## 4. 注釈（枠＋タグ）

図の要素を指して説明するときの標準形。

| 要素 | 色 | コントラスト | なぜ |
| --- | --- | --- | --- |
| 枠 | 専用色相の、白背景で 3:1 を満たす最初の段（色相によって 500〜700） | 白背景で 3:1 以上（非テキストの下限） | 枠は情報を持つ図形なので、非テキストの基準を満たす段を使う |
| タグの塗り＋白文字 | 白文字で 4.5:1 を満たす段の塗り（枠より 1 段以上濃い）＋白文字 | 4.5:1 以上（本文相当） | タグは読む文字を乗せるので、通常の文字コントラスト基準を満たす段まで濃くする |
| ホバー時の強調 | 塗り側は 1 段濃く＋淡いリングを添える | — | 強調は情報を増やさず、目立たせるだけに留める |

- **淡い段（400 相当）は枠に使えない。** 白背景でのコントラストが 3:1 を下回るため、非テキストの下限を満たさない。枠専用の色を選ぶときは、実測してから採用する（`foundations/contrast-and-a11y.md` の計算手順）。
- **枠の当て方は「座標をハードコードしない」。** 対象要素を `relative` な親で包み、枠とタグは `absolute` ＋ `pointer-events-none` で重ねる。実画面の構造が変わっても、要素を包む向きが変わらない限り枠がズレない。
- **タグには `whitespace-nowrap` を必ず付ける。** 細い要素（アイコンの列など）を包むと、絶対配置のタグは shrink-to-fit の幅計算で親の幅まで縮められ、日本語が 1 文字ずつ縦に折り返される。
- 枠・タグはどちらも `aria-hidden="true"` の視覚補助に留める。`button` にしない（ホバーでしか得られない情報を作らない設計にするため。補足文はすべて凡例に常時表示する）。

```tsx
<div className="relative inline-block">
  {children}
  <span aria-hidden className="pointer-events-none absolute -inset-1 rounded-frame border-2 border-<accent>-500" />
  <span aria-hidden className="pointer-events-none absolute -top-2 left-2 whitespace-nowrap rounded-full bg-<accent>-600 px-1.5 py-px text-[10px] leading-tight text-on-brand">
    ①ラベル
  </span>
</div>
```

### 4.1 使い分け（図の大きさで決める）

| 図の大きさ | 注釈の形 |
| --- | --- |
| 大きい図（画面全体・モーダル全体など要素が複数近接する図） | 枠つき（タグ＋枠の両方） |
| 見れば分かる図（要素同士が離れていて、どれを指しているか自明な図） | 枠なし・タグだけ |
| 小さい図（ピル 1 個・トグル 1 個など、指す対象が図全体とほぼ同じ大きさ） | 注釈を付けず、図の下に短い平文を添えるだけ |

小さい図に枠を付けると、タグ（角丸ピル）自体が指している要素より大きくなり、図自体が読めなくなる。**枠が要素そのものより目立ってしまったら、その図は「枠なし」か「注釈なし」まで一段落とす**。

### 4.2 凡例（Legend）

- 凡例（番号つきの補足リスト）を**唯一の情報源**にする。スクリーンリーダーは図やタグを読み上げなくても、凡例だけで内容が分かる状態にする。
- 凡例の番号バッジは `aria-hidden` にしない（凡例が実テキストの情報源であることの一部として、番号自体も読み上げ対象に含める）。
- **凡例の項目にホバーすると、対応する図の注釈を強調する。** 枠を消した図（4.1 の「枠なし」）でも、タグ側を強調できるようにしておく。枠だけを強調対象にしていると、枠なしの図でホバーしても何も起きない状態になり、「対応する箇所が強調される」という凡例の役割が図によって成立したりしなかったりする。

## 5. デスクトップ用とモバイル用の出し分け

- 見本は 768px を境に、デスクトップ用とモバイル用の 2 種類を用意し、どちらか一方だけを描画する。
- 出し分けの判定は **JS（`matchMedia`）で行い、CSS の表示/非表示切り替えに頼らない。** 見本が別レイヤー（モーダル等・フォーカストラップを持つ面）の中にある場合、CSS で隠しただけの側の要素も DOM 上には存在し続け、トラップ側の「フォーカス可能な要素」の走査に混入しうる。JS 側で分岐して非表示側をそもそも描画しなければ、この混入が起きない。
- **見本の境（768px）から、実画面の列がすべて出る幅（例: 1280px）までの中間幅では、実画面のレイアウトがデスクトップ用の見本ともモバイル用の見本とも一致しない**ことがある（サイドバーの一部だけが折りたたみ表示に切り替わる、等）。この中間幅専用の見本を追加で作ると、見本の種類が増えすぎて「画面のどこに何があるか」を伝えるという目的に対して割に合わない。**見本は 2 種類のままにし、狭い幅での収納先を 1 行の注記で補う。**

```tsx
{isDesktop && (
  <p className="text-caption text-on-surface-muted">
    画面が狭いときは、○○は△△にまとまります。
  </p>
)}
```

## 6. 文字を減らすときの注意

見本や凡例の文言を詰めたくなる場面（余白を削る・行間を詰める等）は多いが、**凡例の文言は唯一の情報源**であることを思い出す。見た目を整えるために凡例の文言そのものを削ると、スクリーンリーダー利用者に届く情報がその分減る。詰めてよいのは余白・行間などの見た目の密度だけで、文言の情報量は変えない。

## 7. 落とし穴

- **見本をカードやモーダルと同じレシピで作る。** 段差が付かず、「これは絵です」ということが伝わらない（§2）。
- **見本の中に実物のコンポーネントをそのまま埋め込む。** 操作できてしまう、またはフォーカストラップの走査に混入する（§3）。
- **淡い段の色を枠に使う。** 白背景でのコントラストが非テキストの基準を満たさないまま採用してしまう（§4）。実測せずに「見た目が近いから」で選ばない。
- **小さい図に大きい図と同じ枠つき注釈を付ける。** タグが図より大きくなり、逆に読みにくくなる（§4.1）。
- **枠なしの図で凡例のホバー強調だけ効かなくなる。** 強調の対象を枠だけに限定していると、枠を持たない図で凡例の役割が果たせなくなる（§4.2）。
- **デスクトップ/モバイルの出し分けを CSS の表示切り替えだけで行う。** 非表示側の要素が DOM に残り、フォーカストラップの走査に混入する（§5）。
- **中間幅のために見本を増やす。** 図の種類が増えるほど「実物と見本の対応」を保守するコストが増える。狭い幅の収納先は注記で足りる場合が多い(§5)。
- **余白を削るついでに凡例の文言まで削る。** 唯一の情報源が痩せ、図を見ない利用者に届く情報が減る（§6）。
