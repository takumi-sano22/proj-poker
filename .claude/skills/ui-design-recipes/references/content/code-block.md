# コードブロック

> **いつ読むか**: フェンス付きコード（シンタックスハイライト付き）を表示する画面を作るとき
> **前提**: `foundations/color-usage.md`（役割トークンの体系・状態色の意味）・`foundations/contrast-and-a11y.md`（コントラストの測り方）・`layout/chat-thread.md` §7（横スクロールを出さない組み合わせ）・`components/scrollbar.md`（暗い面のスクロールバー）
> 面の色はトークンの役割名で書く。構文色だけは役割トークンから独立したパレットなので、実装では専用のカスタムプロパティに名前を付けて集約する。

## 1. 要点

- 面（地・ヘッダー・枠・ラベル・ベースの文字色）は**ニュートラルな暗色トークンの段に寄せる**。コードは読む対象だが主役ではないので、明るい面用の役割トークンをそのまま使わない。
- 構文の色分け（キーワード・文字列・数値など）は**役割トークンから独立したパレット**にする。状態色を流用すると「特定の色＝危険・破壊操作」という約束が壊れる。
- 構文色は地の上で AA（4.5:1）を満たす明度に取る。装飾的な文字（コメント等）は「よくある薄さ」をそのまま使うと割ることがあるので実測して調整する。
- テーマは**画面（不透明な面 / 半透明な面のどちらでも）を問わず 1 つに畳む**。見え方のモード差は、コードブロックではなく吹き出し側の面の作り方で付ける。
- ヘッダー（言語ラベル・コピー操作）と横スクロールは**コードブロック自身が持つ**。会話列側は常に横スクロールを許可しない。
- 配布されているハイライト用の CSS テーマはそのまま import せず、色は自分たちのトークン体系に合わせて選ぶ。

## 2. 暗く沈めた面

| 要素 | 役割 | 段の例 |
| --- | --- | --- |
| 地（本文の背景） | 最も暗い段 | 最暗の ink |
| ヘッダー行の背景・下枠 | 地より一段明るい暗色 / 枠色 | 地より 1 段明るい ink とその枠色 |
| 全体の枠線 | 枠色 | ヘッダーと同じ枠色 |
| 言語ラベルの文字色 | 中間の明度 | 中間段の ink |
| ベースの文字色（ハイライト対象外テキスト） | 明るい文字 | 最も明るい段の ink |

- 明るい面用のロールトークン（読む対象の面など）をそのまま流用すると、コード面だけ画面の主役級に明るく浮いて視線を奪う。読む対象ではあるが主役ではないので、**沈めた単色の暗い面**に統一する。

実装の値（`ink` はブランド色相に寄せたニュートラル。`foundations/color-usage.md` §2）:

| 要素 | クラス |
| --- | --- |
| 外枠 | `rounded-lg border border-ink-700 overflow-hidden`＋文字 `text-xs`（会話の中）/ `text-sm`（読み物の中） |
| ヘッダー行 | `flex items-center justify-between gap-2 px-2.5 py-1 border-b bg-ink-800 border-ink-700`、言語ラベル `font-mono truncate text-ink-300` |
| コピー操作 | `shrink-0 px-2 py-0.5 rounded text-ink-200 hover:bg-ink-700 hover:text-on-brand` |
| 本体 | `overflow-x-auto p-2.5 whitespace-pre font-mono leading-relaxed bg-ink-900 text-ink-100 scrollbar-on-dark`＋`role="region"`・`aria-label`（例:「TypeScript のコード」）・`tabIndex={0}`（キーボードで横スクロールできるように） |
| 長いコードの折りたたみ | 20 行を超えたら `max-h-48 overflow-y-hidden` で畳み、下端に地の色から透明への `h-8` のグラデーションを重ね、「続きを表示（全 N 行）」の全幅ボタン（`aria-expanded`＋本体の id を指す `aria-controls`）で開閉する |

構文色の例（Tailwind v3 の既定パレットの明るい段と同じ値。v4 の同名色〔oklch〕でもほぼ同じ見え方。いずれも `ink-900` の地の上で AA）:
キーワード `violet-300`／タグ名・見出し・削除 `rose-400`／リテラル `teal-300`／文字列・追加 `green-300`／数値・属性名・変数 `amber-300`／関数名・リンク `indigo-300`／組み込み `purple-300`。コメントはベースの文字色（`ink-100`）の 62%＋斜体。

## 3. 構文色は独立したパレットにする

構文ハイライトは、キーワード・識別子・リテラル・文字列・数値・関数名・組み込みなどを互いに見分けられる **6〜7 色**を要求する。一方で役割トークンが持つ有彩色は、主となる色相と状態を表す 3 色（成功・警告・危険に相当するもの）しかない。**意味を持つ状態色を構文へ流用すると、状態色が担っている「特定の色＝危険・破壊操作」という約束が壊れる。**

そのため構文色だけは、役割トークンとは別に**独立したパレット**として持つ。

- 値は、テーマのスコープ先頭にカスタムプロパティとして名前付きで集約する（例: キーワード用・識別子用・リテラル用・文字列用・数値用・関数名用・組み込み用の 7 系統）。
- 各色は地（最暗の ink）の上で AA（4.5:1）を満たす明度に個別に選ぶ。役割トークンの流用ではないぶん、コントラストの担保は自分たちで実測して確認する（測り方は `foundations/contrast-and-a11y.md`）。
- ハイライトを行うライブラリが振る分類（キーワード系・識別子系・リテラル系…）をそのまま 7 系統へ寄せて割り当てれば、ライブラリ側の分類ロジックはそのまま使い、色だけを自前にできる。

## 4. コメントの透明度は実測して上げる

補助的な文字（コメント等）を「ベースの文字色を薄める」形で作る場合、装飾で**よく使われる 50% 程度の透明度**をそのまま当てはめると、暗い地の上では AA（4.5:1）を割ることがある。

- 実測して足りない場合は、透明度を上げて調整する（50% では足りず 62% まで上げて初めて基準を満たした例がある）。
- 「装飾的な文字は薄くしてよい」という直感に頼らず、**地との組み合わせで毎回測る**。地の暗さや文字色の段が変われば必要な透明度も変わる。

## 5. テーマは画面を問わず 1 つに畳む

不透明な面（solid）の画面でも、背景を透かす面（glass）の画面でも、コードブロックは**同じ暗色テーマ**を使う。

- コード面は「読むために沈めた面」という役割がどちらの画面でも変わらないため、ここで差を付ける理由が無い。
- 見た目のモード差（不透明度・縁・グラデーションなど）は、コードブロックを包む**吹き出し側**で付ける。コード面自体を画面ごとに複数持つと、色の管理が二重になり、どちらかが更新から取り残されやすい。

## 6. ヘッダーと横スクロールは自分で持つ

- ヘッダー行（言語ラベル + コピー操作）を本体の上に置き、下側に枠線で本体と区切る。言語ラベルは等幅フォント、コピー操作は右寄せにする。
- 本体（コード自体）は折り返さず、**横スクロールはコードブロック自身の内側**に持たせる。会話列全体を横スクロールさせない設計は `layout/chat-thread.md` §7 を参照（幅の広い中身は各自が横スクロールを持つ、という規律の一例がコードブロック）。
- 横スクロールする本体は、キーボードからもフォーカスしてスクロールできるようにする（`tabIndex={0}`＋`role="region"`＋`aria-label`）。マウスやタッチなら横に送れても、フォーカスできないスクロール領域はキーボードだけの利用者には右側が読めない。
- 暗い面の内側をスクロールさせる場合、既定のスクロールバーの配色は明るい面向けの前提で選ばれているため、**暗い面専用のスクロールバー utility**（`components/scrollbar.md` §5）に差し替える。

## 7. 配布のハイライト用 CSS を import しない

シンタックスハイライトのライブラリは、既製の配色テーマ（CSS）を配布していることが多いが、これをそのまま import しない。

- 配布テーマの色は、そのプロジェクト独自の色相・明度で決められており、**このプロジェクトの暗色トークンや AA の実測とは無関係**。地の色を変えたときにテーマ側だけ古いままになったり、地との組み合わせで AA を満たすかを検証していない色をそのまま使うことになる。
- ライブラリは「どの構文要素か」を判定してクラス名を振る部分だけを使い、**色は自分たちで選んで検証する**。ライブラリの分類ロジックとこちらの配色を分離しておけば、地の色や役割トークンの体系が変わっても、構文色側だけを個別に見直せる。

## 8. 落とし穴

- 明るい面用のロールトークンをそのままコード面に使う。画面の中で浮いて見える。
- 状態色（成功・警告・危険に相当するもの）を構文の色分けに流用する。「特定の色＝危険」という約束が壊れる。
- 装飾的な文字の透明度を「よくある値」のまま使い、暗い地の上で AA を割っていることに気づかない。
- 画面（不透明 / 半透明）ごとに別のコードテーマを増やす。モード差は吹き出し側で出すべきものが二重管理になる。
- コードブロックの横スクロールを許すつもりが、会話列側の横スクロール禁止を外してしまう。
- 横スクロールする本体にフォーカスできない（`tabIndex` が無い）。キーボードだけの利用者はコードの右側を読めない。
- 配布されているハイライト用 CSS をそのまま import し、色の対比が自分たちの基準を満たしているか検証しないまま使う。
