# 会話画面（メッセージ列と入力欄）

> **いつ読むか**: チャット・対話形式の画面（メッセージ一覧＋入力欄）を組むとき
> **前提**: `foundations/surface-and-depth.md`（吹き出し＝面のレシピ L1・入力欄＝L2 準主役）・`layout/app-shell-responsive.md`（外枠のスクロールの層）

## 1. 要点

- 会話列の最大幅は **720px** に固定する。読みやすい 1 行の文字数（欧文なら 65〜80 文字相当）から決まる値で、画面が広がっても会話列自体は広げない。
- 吹き出しの幅は相手（アバター付き）と自分（アバター無し）で計算が異なる。**相手側は `calc(100% - アバター列の幅)` で計算し、`max-width:100%` の罠を避ける**（§3）。
- スクロール領域は **枠（`relative`）／スクローラ／中身** の 3 層にし、中身の高さの変化を `ResizeObserver` で見て「下端付近にいたときだけ」追従する。
- 入力ブロックは `fixed` にせず、**会話スクロール領域と兄弟の flex アイテム**として下端に置く。
- 横スクロールは会話列全体では絶対に出さない。**幅の広い中身（表・コード）は各自が `overflow-x-auto` を持つ**設計にする。
- メッセージの操作（コピー等）は hover ではなく**常時表示**にする。タッチ端末には hover が無いため。

## 2. 会話列の最大幅

| 項目 | 値 | Tailwind | 素の CSS |
| --- | --- | --- | --- |
| 会話列の最大幅 | 720px | `max-w-[720px] mx-auto w-full` | `max-width: 720px; margin-inline: auto; width: 100%;` |

- **なぜ 720px か**: AI チャット UI で一般的な本文幅（1 行 65〜80 文字相当）に合わせた値。画面が広がっても会話列自体を広げると、1 行が長くなりすぎて読みにくくなる（可読行長）。広い画面で余った左右のスペースは、補助パネルや対称スペーサー列に回す（`layout/app-shell-responsive.md` §4）。
- 会話列を左右中央に置く帯では `mx-auto` に加えて `w-full` を付ける。`w-full` が無いと、親の flex コンテナ内で `flex-basis: auto` に落ちて中身依存の幅になり、`max-w` が効かない帯が生まれうる。

## 3. 吹き出しの幅

| 主体 | 幅 | Tailwind |
| --- | --- | --- |
| 相手（アバター付き） | `calc(100% - アバター列の幅)`。広い画面（目安 `lg` 以上）では 80% | `max-w-[calc(100%-40px)] lg:max-w-[80%]` |
| 自分（アバター無し） | 常に 80% | `max-w-[80%]` |

- **相手側だけ計算が要る理由**: 相手の行は「アバター列（例: 32px の丸＋8px の間隔＝40px・`flex-shrink-0`）」と「吹き出しラッパ」が横に並ぶ `flex` 行になっている。`max-width: 100%` は**フレックスコンテナの全幅**に対して解決されるため、そのままだと行の必要幅が「アバター列 + 100%」になり、アバター列の分だけ必ずはみ出す。フレックスアイテムの既定の縮小（`min-width: auto` → `flex-shrink`）はこの「max-width で頭打ちにされた 100%」には効かない（実測で確認済み。はみ出し分だけ親のスクロール領域が横スクロール可能になる）。**対処はアバター列の分を `max-width` の計算式自体から引くこと**（`calc(100% - 40px)`）。アバター列のサイズを変えたら、この計算式の値も同じ箇所から必ず一緒に直す（別々の場所に同じ値をコピーしない）。
- **自分側にアバター列が無い理由**: 自分の発言は行の唯一の子要素（`justify-end` の中に 1 つ）なので、`max-width` を絞っても右端は親の右端のまま。アバター列の干渉が無いため、計算式ではなく固定の 80% で足りる。
- 広い画面で 80% を掛けるのは「相手の発話とユーザー発話が、幅だけでは見分けがつかないほど画面端近くまで伸びる」ことを避けるため。**狭い画面では 80% を掛けない**（元々の会話列自体が狭く、80% にすると逆に窮屈になる）。

## 4. 一覧の余白と間隔

| 項目 | 値 | Tailwind |
| --- | --- | --- |
| 一覧の左右余白（狭い画面） | 8px | `px-2` |
| 一覧の左右余白（広い画面・目安 `lg` 以上） | 16px | `lg:px-4` |
| 一覧の上下余白 | 16px | `py-4` |
| メッセージ間の間隔 | 16px | `space-y-4` |
| アバターとテキストの間隔 | 8px | `mr-2` |

- 狭い画面ほど左右余白を詰め、吹き出し側の `max-width` も緩めているため、詰めた分だけ吹き出しが画面幅いっぱいに近づく。

## 5. スクロールの 3 層と追従

```
<div class="relative flex-1 min-h-0">        ← 枠。浮かせるボタン（最新へ戻る）の基準
  <div class="h-full overflow-y-auto overflow-x-hidden">  ← スクローラ
    <div class="space-y-4">…メッセージ…</div>             ← 中身（ResizeObserver の観測対象）
  </div>
  <button class="absolute …">最新へ戻る</button>          ← スクローラの外（一緒にスクロールさせない）
</div>
```

- **3 層に分ける理由**: 「最新へ戻る」のような浮かせるボタンをスクローラの中に置くと、一緒にスクロールしてしまい会話の上に固定されない。枠（`relative`）を追加してボタンをその直下に `absolute` で置き、スクローラとは独立させる。
- **追従は「中身の高さが変わったこと」を `ResizeObserver` で見る。** メッセージの配列や文字列を直接 deps にすると、内容が同じでも呼び出し側が毎レンダー新しい要素を組み立てるケース（例: 追加のスロット要素）で無関係な再実行が起きる。高さの変化だけを見れば、関係ない再レンダーでは発火せず、逆に配列を経由しない中身の増減（提案リストの出現など）も取りこぼさない。
- **「下端にいたか」は伸びる前の高さで判定する。** 伸びた後の値で判定すると、増えた分だけ必ず「下端から離れている」と出てしまい、一度も自動追従しなくなる。伸びる直前の `scrollHeight` / `clientHeight` を ref に保持し、`ResizeObserver` のコールバック内でまず新しい値を保存してから、保存しておいた「伸びる前の値」で下端判定を行う。
- **初回のコールバックだけは判定せず、必ず最新へ飛ばす。** `observe` した瞬間に 1 回鳴るが、そのとき「伸びる前の値」は
  いまの高さなので、**既にメッセージがある状態でマウントすると必ず「離れている」と判定されて先頭に留まる**。
  表示の切り替え（別ウィンドウに切り出す・表示モードを変える・幅の閾値をまたぐ）で再マウントされる画面では必ず踏む。
  最初の 1 回を目印（`let first = true`）で見分け、そのときだけ `scrollToBottom()` する。
- **スクロール領域自身のサイズ変化も観測する。** 入力欄が内容に応じて伸びると、その分だけ会話スクロール領域の `clientHeight` が縮む。中身（メッセージ）は変わらないので中身側の `ResizeObserver` は鳴らず、スクロールもしていないので `scroll` イベントも出ない。結果、次に何かが届いたときの下端判定が誤り、追従が止まる。**中身とスクロール領域の両方を `observe` する。**
- **追従の移動は `instant`（即時）にし、`smooth` にしない。** 生成中は中身が繰り返し伸びるため、`smooth` だとアニメーションの完了前に次の伸びが来て、下端に追いつけないまま「離れている」と判定されて追従が止まる。ユーザーが明示的にボタンを押して戻るときだけ `smooth` を使う。
- **`scrollIntoView` ではなくスクロール領域自身を動かす。** 末尾のダミー要素へ `scrollIntoView` する方式だと、その要素より後に何か描画が増えたときに手前で止まってしまう。スクロール領域の `scrollHeight` を目標にすれば、中身の並び順に依存しない。
- **「最新へ戻る」ボタンはスクローラの外**（枠の直下・`absolute`）に置く。会話の上に浮かせたまま、スクロール操作とは独立させるため。下端から離れた状態が一定時間続いたときだけ出す（チラつき防止。目安 3 秒程度の遅延）。
- **下端の許容幅を 0 にしない。** 0 にすると、行の端数やスクロール位置の丸め誤差だけで「離れている」と誤判定し、追従が途切れたりボタンが出っぱなしになる。数十 px 程度の許容幅（例: 48px）を持たせる。

## 6. 入力ブロックの置き方

- **`fixed` にせず、会話スクロール領域と同じ親の中で flex の兄弟として下端に置く。** 外枠が `flex flex-col` の縦積みなら、スクロール領域（`flex-1 min-h-0`）の直後に入力ブロック（`shrink-0`）を並べるだけで、自然に下端へ収まる。`fixed` にすると、ソフトキーボード表示時のレイアウト計算やスクロール領域の高さ計算を別途自前で行う必要が生じる。
- **器の意匠**: 半透明＋ぼかし＋上向きの影で「浮いている」ことを示す（面のレシピ L2 準主役・器。`foundations/surface-and-depth.md` §5）。上側の罫線は外し、上向きの影がその役割を兼ねる。

  | 項目 | 値 | Tailwind |
  | --- | --- | --- |
  | 器の背景 | 明るい面の 80% 透過＋ぼかし | `bg-surface-raised/80 backdrop-blur-md` |
  | 角丸 | card 相当 | `rounded-card` |
  | 影 | 上向き（raise-up） | `shadow-raise-up` |
  | 画面下端との距離 | 16px | `mb-4` |

- **送信ボタンと入力欄の寸法**:

  | 項目 | 値 | Tailwind |
  | --- | --- | --- |
  | 送信ボタン | 44×44px の正方形 | `h-11 w-11` |
  | 入力欄（textarea）の左右余白 | 16px | `px-4` |
  | 入力欄の上下余白 | 12px | `py-3` |
  | textarea の最大高さ（自動伸長の上限） | 120px | `Math.min(el.scrollHeight, 120)` を style で反映 |
  | 送信ボタンと入力欄の間隔 | 8px | `gap-2` |

## 7. 横スクロールを出さない組み合わせ

- 会話列のスクロール領域には **`overflow-y-auto` に加えて `overflow-x-hidden` を明示する。** CSS の仕様上、片方の軸が `visible` 以外だと、もう片方の軸も暗黙に `auto` へ強制される。つまり `overflow-y-auto` だけを指定していても、中の何かが 1px でもはみ出せば会話列全体が横スクロール可能になってしまう。`overflow-x-hidden` は**再発ガード**として明示する。
- 吹き出し本文には **`break-words`（`overflow-wrap: break-word`）を付ける。** スペースを含まない長い連続文字列（長い URL 等）は、指定が無いと `max-width` のコンテナを突き破って横方向へ伸び、それがスクロール領域の横スクロールとして表出する。`overflow-wrap` は継承されるプロパティなので、吹き出し内側の本文（見出し・段落など）にも及び、二重に指定する必要はない。
- **幅の広い中身（表・コードブロック）は、会話列側で横スクロールを許すのではなく、各自が `overflow-x-auto` を持つ。** 会話列そのものは常に `overflow-x-hidden` のままにし、表やコードのような「行の外へはみ出してよい」要素だけが自分の内側でスクロールする。会話列側で横スクロールを許すと、その一部の要素のためだけに画面全体が左右に動く体験になる。

## 8. メッセージの操作を常時表示にする理由

- コピー・作り直し等の操作行を **hover で出す方式にしない。** タッチ端末には hover という概念が無く、操作の存在に気づけないか、意図しないタップで一瞬だけ表示されて押しそこねる。
- 代わりに**常時表示にしつつ、文字を小さく・淡くする**ことで、会話の読みの邪魔にならない見た目に寄せる。「常に見えるが、目立たない」という両立をフォントサイズと濃淡だけで作る。
- 操作行は吹き出しの中ではなく、**吹き出しの外・直下**に置く。吹き出しの中に混ぜると、操作要素の分だけ吹き出しが縦に伸びて会話が読みにくくなる。DOM の順序は「本文 →（出典等の補足）→ 操作」のままにし、読み上げ順もそれに従わせる。

## 9. 落とし穴

- **アバター列の幅を変えたのに、相手側 `max-width` の計算式（§3）を直し忘れる。** 症状はすぐには出ず、「吹き出しが数 px だけ欠ける」ように見えるだけなので気づきにくい（`overflow-x-hidden` があると横スクロールという分かりやすい症状にもならない）。2 箇所（吹き出し本文と、生成中のプレースホルダ吹き出し）に同じ計算式を使っている場合は両方直す。
- **「下端にいたか」を伸びた後の高さで判定する。** 常に「離れている」と判定されて追従が二度と効かなくなる（§5）。
- **`scrollTo` の `behavior` に `"auto"` を使う。** `"auto"` は「その要素の CSS `scroll-behavior` に従う」という意味であって「即時」ではない。将来どこかで `scroll-behavior: smooth` を指定すると、追従が黙って `smooth` に戻り、生成中に追いつけなくなる不具合が再発する。即時にしたいときは `"instant"` を明示する。
- **初回のコールバックも「伸びる前の高さ」で判定する。** メッセージがある状態でマウントすると先頭に留まる（§5）。
- **入力欄の伸縮でスクロール領域が縮んだのに、それを観測していない。** 中身は変わっていないため中身側の `ResizeObserver` が鳴らず、次の追従判定を誤る（§5）。
