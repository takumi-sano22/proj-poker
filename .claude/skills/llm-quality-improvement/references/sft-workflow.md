# SFT 実務リファレンス（教師データ・学習・tuned 評価）

> **現時点で proj-poker に SFT の採用予定はない（参考資料）。** プロバイダは Claude API で、ファインチューニングの可否・提供形態は採用時に再調査する。以下は他PJ（マネージド SFT）の知見を保存したもので、GCP/Vertex 固有の記述（endpoint・IAM・マネージドジョブ）は proj-poker にそのまま当てはまらない。採用を検討する場合は `docs/decision_log.yaml` の方針（LLM は合法候補から戦略選択のみ・D40）との整合を先に確認し、`docs/11_OPEN_ITEMS.md` へ起票する。

プロンプト改善で頭打ちになった／推論時コスト（長いプロンプト）を学習へ寄せたい、という
段階で読む。前提として measurement-ops.md の測定基盤が動いていること（測れない状態で
学習しても効果を判定できない）。

## 目次

1. 着手前の判断
2. 教師データの作成と検品ループ
3. プロンプトと教師信号の一致（最重要）
4. 学習の実行と診断
5. tuned モデルの評価
6. 本番切替と運用

## 1. 着手前の判断

- SFT の前に「プロンプトの指示と、教師データが示す変換は一致しているか」を必ず確認する
  （§3）。不一致のまま学習すると効果が出ず、学習費と時間を失う。
- 費用は `billableTokenCount（データセット 1 周分）× epoch × 単価` で見積もる。
  プロンプト圧縮はデータセットを軽くし学習費も下げる（一石二鳥）。
- tuned モデルの推論単価は base の定数倍になるのが普通。切替後の 1 応答単価を
  「トークン実測中央値 × 単価」で前後比較できるよう、事前にベースラインの usage を残す。

## 2. 教師データの作成と検品ループ

- **少数抽出 → 人間検品 → 作法の言語化 → 全体反映**のループで作る。全件を人間が書くのではなく、
  機械生成した候補を人間が検品し、指摘を「作法」（例: 核となる要素は言い換えて残す・
  長い助言は圧縮する）として言語化してから残り全体へ機械適用する。
- 検品の修正は **rewrites（書き換え）と除外（exclusions）を別ファイルで管理**し、
  再生成（assemble）を冪等にする。「何件がなぜ除外されたか」は後で必ず聞かれる。
- 教師データを再構築したら、**変えていない部分が変わっていないことを機械検証**する
  （例: 会話 contents のバイト不変・件数一致）。「プロンプトだけ差し替えたつもり」は
  検証しないと信用できない。
- 教師の理想回答が満たすべき水準（字数・スタイル記号の露出率・安全度別の勾配）を
  機械集計して記録しておく。学習後の副作用検出（§5）の基準になる。

## 3. プロンプトと教師信号の一致（最重要）

**システムプロンプトの保守的な指示（「意味を絶対に変えるな」「言い換えのみ」）と、
教師データが示す大胆な変換（圧縮・追加・再構成）が矛盾していると、プロンプトが
prior として学習信号を打ち消し、SFT が効かない。**

- 学習を回す前に、教師データの入力に入るシステムプロンプトを「教師の変換をそのまま
  指示として言語化したもの」へ再設計する（検品で言語化した作法を指示に昇格させる）。
- 字数の指示は出力の中身を決める（下限が長いと修飾で埋める）。教師の実分布に合わせる。
- 「〜のときに限り」の条件はプロンプト指示でなく構造ゲート（boolean で文ごと出し分け）に。
- few-shot は捏造せず**教師データの実例**から選ぶ（入力行つきで）。安全側の見本は
  軽い見本とは別に用意し、「軽さを持ち込まない」変換の例を置く。
- プロンプトを再設計したら base モデルでも品質が上がることがある（それ自体が成果）。
  **改稿効果と SFT 効果は 4 系列比較（base×旧P / tuned×旧P / base×新P / tuned×新P）で分離**する。

## 4. 学習の実行と診断

- **停滞（エラーなしで学習が始まらない）はマネージド SFT の既知パターン**。数時間動かず
  再投入する場合は、**必ず旧ジョブをキャンセルし、終端状態（CANCELLED 等）を API で確認してから**
  投入する。停滞ジョブは後から動き出すことがあり、放置したまま再投入すると並行実行で
  二重課金・リソース競合になる（並行ジョブ枠も消費する）。キャンセルの課金は学習処理分のみ
  なので、未処理での停滞なら費用は発生しない。
- **undertrained の診断**: train 精度が横ばい・val loss が下降中のまま終了なら学習圧不足。
  epoch・学習率・アダプタサイズを同時に増やしてよい（学習は「1 回 1 変更」の例外。
  ただし評価で効果を分離できる設計は保つ）。
- **軽い過学習の判定**: val loss が反転し val 精度が微減した epoch が過学習の入口。
  ただし採用判断は loss でなく**下流の品質評価**で行う（loss 最適の checkpoint より
  最終 epoch の方が下流評価で全軸上回ることがある。実測して決める）。
- checkpoint ごとの loss・精度表は消える前に控える（コンソールのみで API から取れない
  ことがある）。

## 5. tuned モデルの評価

- **学習に使った実物の model_input をそのまま投げる**（プロンプト再構築をしない）。
  base⇔tuned で入力が完全一致するペアを作るため。
- **「効果なし」を確定できる設計にする**: Judge 全軸・文字類似度・目視の独立 3 証拠が
  ±ノイズ内なら効果なし。1 日で確定できれば方針転換が早い（効果なしの確定は失敗ではなく
  測定基盤が機能した証拠）。
- **SFT シグネチャ**: 「理想への類似度が上がり、変換元テキストへの類似度が下がる」が
  狙いどおり学習された形。train/val で分けて見る（val のみに出るなら汎化・train にも
  出ないなら未学習）。
- **副作用を決定論で監視する**: SFT は教師の平均へ寄せる過程で、低頻度のスタイル記号
  （口癖・質問での終わり方）を教師水準以下まで潰すことがある。特定語の露出率・質問率・
  必須トークン（do_not_change）の保持率を学習前後で機械集計して比べる。
- val を HP 選定にも使ったなら、それは厳密な held-out ではない。断定を「検証セット上の
  改善」に限定し、完全独立テストは別途とする。

## 6. 本番切替と運用

- 切替はモデル ID の env 1 つで済む設計にしておく（tuned endpoint のリソース名を判定して
  専用経路・単価・クォータ重みへ自動分岐）。ロールバックも env を戻すだけにする。
- tuned 限定のフォールバック（失敗時に base で 1 回引き直す）を入れ、発火回数を
  トレースで数えられるようにする（モデル名がフォールバック先に切り替わる形で記録）。
- 切替直後の実運用レイテンシは n が小さく統計にならない。暫定値と明記し 1 週間後に再測する。
- tuned モデルは基盤モデル上のアダプタで**エクスポート・プロジェクト間コピーが不可**な
  ことがある（マネージドサービスの制約）。マルチ環境で使うなら越境 IAM 等の設計を
  切替前に確認する。
