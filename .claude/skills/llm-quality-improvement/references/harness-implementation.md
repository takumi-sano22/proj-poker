# 評価ハーネス実装リファレンス

評価ハーネス（生成バッチ・Judge 採点バッチ）を新規実装・改修するときに読む。
ここの作法はどれも「静かに壊れた測定」を経験して確立したもの。

## 目次

1. 本番経路の複製
2. データ整合のガード
3. 決定論指標の併用
4. 集計と転記の規律

## 1. 本番経路の複製

- **モデル解決・生成設定（temperature / thinking）・プロバイダ分岐・後処理を本番実装と共有する。**
  ハーネス独自の呼び出しを書くと、一致条件を 1 つ直すたびに別の不一致が生まれる。
  本番のモデル解決（role-based config の resolve 系関数。Opponent / Review の role ごとに Claude API の Model を引く。OI-001）を import して使うのが最も安全。
- 環境変数で本番と同じ構成を明示注入する（role ごとのモデル設定・API キー参照・温度などの生成設定。キー自体は記録しない）。
  「たぶん同じ既定値」に頼らず、run の config として summary に記録する。
- E2E 型（Hand を頭から再生）と単発型（固定 Spot 1 件 → 1 Action / 1 Review）を区別する。E2E は前段の Action 選択が
  後段の局面を変えるため、前段のブレで比較対象の Spot が揃わなくなる。単発型の固定 Regression Case を基本とし、除外件数と理由を必ず記録する。

## 2. データ整合のガード

いずれも「無いと静かに壊れる」ことを実測済みのガード:

- **母集団照合**: 採点対象の jsonl が期待母集団（meta ファイル）と完全一致しなければ停止する。
  部分実行の結果で正常な summary が出ると、系列間比較が静かに崩れる。
- **再開ガード**: 中断・429 対応のため「同一構成の成功行のみスキップ」で再実行できるようにする。
  スキップ判定には構成（モデル・Judge・入力ハッシュ）を含め、構成が変わったら再採点させる。
- **空出力は失敗扱い**: 空文字を成功として保存すると、下流で「既存値を null 上書き」の
  ような事故につながる。
- **--limit 等の部分実行では summary を更新しない**（部分集合の summary は誤読のもと）。
- 失敗行を残したまま summary を生成しない（失敗残があれば exit 非 0 で再実行を促す）。

## 3. 決定論指標の併用

- Judge と独立に、正規表現・カウントで測れるものは決定論で測る:
  Structured Output の schema 検証／選択 Action が合法候補集合に含まれるか（Illegal Action）／Retry 回数／Latency／
  Pass A の入力に判断時点より後の情報が含まれないか（Hindsight Leak）／Math（Pot Odds・Equity）の再計算照合／
  KB / Source の引用が実在するか（Source Grounding）／Persona 別の Action 分布。
- 決定論指標は **Judge のバージョンに依存しないため、時系列で比較できる唯一の系列**。
  Judge を改訂しても決定論だけは過去と直接比較できるよう、定義を安定させる。
- 「判定に使う指標」と「参考値」を明示的に分ける。相関しないと判明した指標
  （例: 特定語の露出率 ≠ Persona の差別化）は判定から外し、参考値へ格下げした経緯ごと記録する。

## 4. 集計と転記の規律

- **数表はスクリプトで生成する**。文書に手で書いた表は、書いた本人の記憶違いが混入する
  （他PJでの実測: 記憶で書いたカテゴリ表が実データと大きく食い違った）。
- 手で転記した数値は、一次データとの**突合スクリプト**で機械照合してから公開する。
- subagent に集計・調査を委譲した場合、本文に載せる数値は親が一次ファイルで裏取りする。
- 二次記録（手書きの履歴 md）と raw（summary.json）が食い違ったら raw を正とし、
  食い違いの存在自体を注記する（黙って直さない）。
- レイテンシ等の環境依存値には環境起因の異常（時計ドリフトによる負値など）が混入しうる。
  異常値の検出ルールと除外方針をデータ側の NOTES に残す。
