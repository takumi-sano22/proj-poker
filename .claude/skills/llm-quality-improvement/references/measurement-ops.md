## 1. LLM-as-a-Judge の設計

### 軸の設計と改訂

- **軸は 10 個程度に抑える**。増やしすぎると 1 軸あたりの採点が薄まり、どの軸も動かなくなる。
  新しい観点が要るときは追加ではなく**統廃合**を検討する（他PJ由来の例: 「好感度」を別軸へ、
  「淡白さ」を別軸 + 失敗フラグへ吸収して廃止。proj-poker なら Persona の「攻撃性」と「ブラフ頻度」の重複軸など）。
- **「無い」と「やり過ぎ」が同じ点数になる軸は情報が潰れている**。1 点の意味を分解し、
  中間点の定義を書き直す（例: Persona の差が全く出ない = 2 点・Persona が極端で不自然 = 1 点と分ける）。
- 軸の定義には**5 点⇔1 点の具体的な判定基準**を書く。「〜らしさ」のような抽象語だけの軸は
  採点が揺れる。
- **状況によって採点対象外になる軸は null にする**（例: Solver 非対応の Spot では Solver 一致度の軸を採点しない。Unsupported Solver Spot は正常 Fallback）。
  0 点扱いにすると平均が壊れ、無理に採点すると「高リスクで軽口を出す」方向の圧になる。
- 軸スコアと別に**失敗フラグ（boolean）**を持つ。平均では潰れる低頻度の致命傷
  （Illegal Action・Hindsight Leak・Hidden Information Leakage・Math 誤り・Source Grounding 欠落・Strategic Incoherence・幻覚）を
  件数で拾うため。

### 採点モデルの選択と検証

- 被験系と同一モデルを Judge にしない（自己選好バイアス）。Opponent（Haiku 級）の Judge は Review 用の上位モデルなど 1 段上を使う。モデルは role-based config から解決し、Judge 用の role も設定で分ける（OI-001）。
- **Judge の絶対値はモデル依存**。上位モデルで 10% を再採点すると、定性的な軸は
  0.4〜0.7 辛くなることがある（他PJでの実測）（±1 一致率 90%+ なら相対比較としては有効）。
  スコアは「同一 Judge 内の相対比較」でのみ使い、外部基準と絶対値比較しない。
- Judge モデル・criteria バージョンは結果行に埋め込む（後から「どの Judge の値か」を
  機械判定できるようにする）。

### 理想参照の設計

- 「何に近づけたいか」の理想参照は複数ありうる（Human-reviewed Hand の模範 Review・Solver 出力など）。**参照が違えば別の指標**として扱い、名前でも区別する。
- 理想参照つきの E2E 再生（Hand を頭から流す）は、履歴が自前の生成で進むため参照とのずれが
  蓄積する。固定 Spot の 1 対 1 評価より値が低く出るのは構造的なもので、劣化ではない。

## 2. 測定の計画と実行

- **手順**: criteria 固定（コミット）→ ミニプローブ（1〜数件で配線確認）→ 本測定 →
  集計 → 記録。プローブを飛ばすと 30 分の本測定が env ミスで無駄になる。
- **run 間ばらつきを最初に測る**（同一構成で 2〜3 run）。改善ラインはその約 3 倍。
- **プロンプト比較は文字列 diff で**。「この意図で変えたはず」ではなく、旧版を
  `git archive` で展開して実体を比較する。意図と実体はよくずれる（few-shot の
  取り違え・置換の空振り）。
- **不変条件は別バッチでゲートする**。品質改善の測定（少数・特定 Spot）と、不変条件の確認
  （Illegal Action・Hindsight Leak・Hidden Information Leakage を全 Regression Case で数えるフルバッチ）は目的が違う。
  プロンプトや入力組み立てに関わる変更は、マージ前に不変条件バッチを 1 回通す。
- **測り直しが必要になる変更を知る**: プロンプトの大改稿は既存ベースラインを陳腐化させる。
  「どの測定が無効になったか」を変更時に明記し、取り直しを積み残しリストに載せる。

## 3. レート制限・環境起因の乱れへの対処

- 429 / overloaded（Claude API のレート制限・容量逼迫）は**再開ガードつきのバッチで「完走→失敗分だけ再実行」**
  が基本。パスを分けて回収し、全件成功するまで summary を出さない設計にする（部分集合で
  正常な summary が出ると母集団一致が静かに崩れる）。
- delay を上げても capacity 系の 429 は消えないことがある。失敗率が高い時間帯は
  仕切り直しの方が総所要が短い。
- 利用上限のある経路をハーネスが踏むと、計測自体が壊れる（Fallback の混入で
  Illegal Action「0 回」のような誤測定になる）。**計測前に経路とクォータを確認**し、Fallback 発火は別カウントで記録する。
- レイテンシを `Date.now()` 差分で測る場合、実行環境の時計同期（NTP 巻き戻し）で
  負値が混入しうる。負値は無効として除外し、系列間レイテンシは参考値扱いにする。
  確定値が要るなら本番側の記録（Event Log / LLM 呼び出しトレース）を正とする。

## 4. 品質スナップショット文書の書き方

「改善の経緯」と「現在いくつか」は別の文書。スナップショットは以下を守る:

- **全数表に 8 点セット**を付ける: 指標名（英名+日本語）／母集団（n・分割）／Judge
  （criteria 版 + モデル）／理想参照／被験構成（モデル・プロンプトの版）／値／
  一次データのパス／**比較可否（どの既存系列と並べてよい/いけないか）**。
- 冒頭に「本文書内の表同士の比較可否マップ」を置く。
- **未測定項目を理由つきで明示する**（黙って落とさない）。実施できない理由
  （API コスト・Regression Case 不足・Solver 未整備）と、後で実行する手順を書く。
- 判断が要る所見は「人間判断の論点」として分離し、文書は判断材料の提示までに留める。
- 読者がリポジトリへアクセスできない前提なら、数値は転記する（パス参照だけにしない）。
