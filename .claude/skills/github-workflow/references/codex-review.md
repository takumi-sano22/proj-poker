# Codex レビュー手順（詳細）

`github-workflow` skill「PR作成後のレビューフロー / Step 2-A: Codex レビュー（Codex 導入環境）」の詳細メカニクス。本文（SKILL.md）はマージ判断に直結する骨子だけを持ち、実行・監視・判定・打ち切りの手順はここを一次情報とする。

> **前提（SKILL.md と共通）**: Codex ツールは `~/bin`（`codex-sample/install.sh` の配置先）に置かれ **PATH に無い**のが普通。`codex-mode.sh` / `codex-review.sh` は必ずフルパス（`~/bin/...`）で呼ぶ（名前だけでは `which`/`find` でも拾えない）。**マージ判断の前に必ず `~/bin/codex-mode.sh get` でモードを確認する**（省略禁止）。Codex 未導入環境の手順は [`non-codex-review.md`](non-codex-review.md)。

---

## バックグラウンド実行と監視

**Codex レビューはバックグラウンド実行し、完了通知＋壁時計タイムアウトで監視する**（`codex exec review` は数分かかり、フォアグラウンド同期実行だとハング時にセッションを止めてしまうため）。

- `~/bin/codex-review.sh --pr <PR番号>` を **Bash の `run_in_background: true`** で起動する。
- **`codex-review.sh` は codex の stdout/stderr を一時ファイルへ退避するため、バックグラウンド出力には開始ログ以降、完了まで進捗が出ない。**「無出力＝ハング」で判定してはならない（正常でも時間のかかる大きめ PR を誤停止する）。
- 完了はハーネスが通知するので、それを待って `STATUS=` 行で結果を判定する。数分間隔（`ScheduleWakeup` 等）のヘルスチェックは、**プロセスがまだ生存しているかの確認に留める**（進捗ログの更新有無では判定しない）。
- **ハングの判定は壁時計の絶対上限で行う**（目安: 起動から 15〜20 分経っても完了通知が来ない場合）。上限を超えたら当該バックグラウンドプロセスを停止し、`error` 相当として要点を伝えて停止する（無限ブロックを避ける）。

## STATUS 判定

出力末尾の `STATUS=` と終了コードで結果を判定する:

| STATUS | 終了コード | 意味 |
|---|---|---|
| `clean` | 0 | P0/P1 指摘なし（マージ可） |
| `findings` | 10 | P0/P1 指摘あり（コメント投稿済み） |
| `halt-tokenlimit` | 20 | トークン制限 & 停止ポリシー（人間確認） |
| `error` | 1 | 実行失敗 |

`error` / `halt-tokenlimit` は、いずれのモードでも**マージ・自走をせず**、要点を伝えて停止する。

> **`codex-review.sh` は STATUS に関わらずレビュー本文を PR にコメントする**（`POST=ok`）。ただし投稿だけ失敗することがあり（`POST=failed`。本文は `POST_BODY_FILE` に残る）、また本文には Claude 側の判定（4 状態・accept・マージ可否）が無い。そのため **STATUS に関わらず、Claude 側でも判定結果を PR コメントに投稿する**（`POST=failed` なら本文も併せて投稿し直す）（`## 🤖 Codex レビュー結果` 見出しで `STATUS`・観点結果・対応/残課題・マージ可否を記載。`gh pr comment <PR番号> --body ...`）。投稿しないと `clean` レビューが PR 上に残らず、Codex 済みか追えないままマージする事故になる。

## モード別処理

- **stop**: Codex を実行せず、マージもしない（人間に委ねる）。
- **prereview**: Codex を実行するが、結果に関わらずマージしない。`findings` の場合はコメントが残るので、要点を伝えて人間レビューを促す。
- **review-merge**:
  - `clean`（本文の `[P2]` は修正か accept 記録済み）かつ「人間確認が必要な条件」に該当しなければ、コメント本体を直読したうえで `gh pr merge` する。
  - `findings`（P0 / P1）は下記「finding の処理」で処理する —— 4 状態に確定 → CONFIRMED は same-root sweep して修正 → push → **条件付き再レビュー**（P0 / P1 の修正は再実行必須）。人間確定区分の指摘は修正せず記録して停止。
  - 修正→再レビューの往復は**同じ問題のループなら 3 回で止めて人間へ返す**。各回が別の妥当な指摘なら内容で続行を判断する（上限を引き上げるのではなく、同じ形の指摘が 3 回続いたら構造を変える。下記「長期反復」）。
  - 記録系 docs だけの差分は Codex をスキップできる（下記「記録系 docs の Codex スキップ」）。
- **autonomous**: `review-merge` と同じ処理を、Issue をまたいで自走する（マージ後に次の Issue へ進む）。停止条件・上限は同じ。

「人間確認が必要な条件」は SKILL.md「必ず人間確認で停止する条件」を参照。

## finding の処理（4 状態・same-root sweep・P2 accept）

指摘を受けたら**即修正せず**、次の順で処理する。狙いは「指摘を直したら同根の別箇所が次巡で指摘される」「P2 を clean にするまで往復する」を畳むこと（実例: 設計 PR で 20 巡、別 PR で 11 巡に及んだ）。自己レビューの指摘でも Codex の指摘でも同じ手順を通す。

### 1. finding を 4 状態に確定する（validation）

| 状態 | 意味 | 扱い |
|---|---|---|
| `CONFIRMED` | 差分・再現・仕様から欠陥の実在を示せた | 手順 2 へ（sweep → 修正、または P2 accept） |
| `FALSE_POSITIVE` | 前提が成立しない・誤読 | **コードを変えない**。根拠を PR コメントへ記録して閉じる。同じ指摘で修正の往復をしない |
| `DESIGN_DISAGREEMENT` | 実装は意図どおりで、設計判断の相違 | 同上。ユーザー確定済みの決定と対立する再提起は人間へ返す |
| `UNPROVEN` | 実在も不在も示せない | severity と検証コストで決める。**P0 / P1 級の UNPROVEN を未検証のままマージしない**（検証して確定させるか人間へ返す） |

- 検証の根拠は差分・再現・仕様であって、指摘文の説得力ではない。安価に再現できるものは「修正前に失敗する確認 → 修正 → 通る」を優先する（全 finding のテスト化は義務にしない）。
- **確定の責任者**: security・認証/認可・権限・課金・アーキテクチャ境界に関わる指摘は**人間が確定**（採否の提案を PR コメントへ記録して停止）。それ以外（明確なバグ・保守性・スタイル）は Claude が確定してよい。
- 各 finding の最終状態・採否・理由・修正コミットを PR コメント（自己レビューコメントへの追記または `## 🤖 Codex レビュー結果`）に残す。無言で全採用・全無視しない。

### 2. CONFIRMED は same-root sweep してから直す

行単位で直して終わらせず、**同じ failure mechanism を共有する範囲**を先に確認してから push する（同根を残したまま push すると、次巡が同じ root failure class を指摘し直す）:

| 範囲 | 例 |
|---|---|
| 同じ関数・ファイル | 同じ関数内の同型の未検査 |
| 同型の実装群 | 兄弟の Route Handler・同じ parser・同じ hook の呼び出し元 |
| 契約の両側 | API とクライアント、producer と consumer、状態機械の全遷移 |
| リポジトリ横断 | 共通 API・rename・横断的なセキュリティ規則 |

差分外で見つかった同根は **Issue へ分離**する（scope へ勝手に足さない）。差分内の同根は同じ修正に含める。探索は `Explore` へ委譲してよい（全文を親へ戻さない）。

### 3. P2 は根拠付きで見送れる（P2 accept）

`[P2]` に限り、次のいずれかを根拠に**人間承認なしで修正せず見送れる**。`[P0]` / `[P1]` は accept できない（マージ前に解消必須）。**security・認証/認可・権限・課金・アーキテクチャ境界に関わる `[P2]` は accept の対象外**（手順 1 の「確定の責任者」どおり人間が確定する。Claude が単独で見送らない）。

1. finding の前提がこの文脈では成立しない
2. リスクに対して修正コストが上回る
3. 修正しないほうが全体として安全（修正が別の失敗を作る）

**記録が無い見送りは accept ではない**。PR コメントへ次の形で残す（`## 🤖 Codex レビュー結果` の中でよい）:

```markdown
### P2 accept
- <finding の識別（file:line または見出し）>: 根拠 <1〜3 のどれか> —— <1〜2 行の説明>
```

### 4. 条件付き再レビュー（修正 push 後に Codex を回し直すか）

| 修正の内容 | 再実行 |
|---|---|
| `[P0]` / `[P1]` を修正した | **必須**（省くなら自律マージを放棄して人間へ返す） |
| `[P2]` だけを修正し、次の**どれにも当たらない**: ①security / 認証・認可 / 契約境界に触れた ②sweep が想定より広がった ③修正が新しい failure mode を作りうる ④`origin/main` の取り込みでレビュー済みの前提が変わった | **不要**。プロジェクトの品質チェック（例: `npm run lint` / `npx tsc --noEmit` / `npm run format:check`）を通してマージ可 |
| `[P2]` の修正が上の①〜④のどれかに当たる | 必須。**①に当たる修正は再実行に加えて「必ず人間確認で停止する条件」の対象**（自律マージしない） |
| accept・記録だけでコード差分が無い | 不要（レビュー済み SHA から差分が変わっていない） |

再実行しないと決めたら、その判断と根拠（どの条件に当たらないか）を PR コメントへ 1 行残す。**「必ず再実行」は P0 / P1 修正と①〜④に当たる修正にだけ掛かる**（従来の「修正をプッシュしたら必ず再実行」を本表で置き換える）。

### 5. 終了条件とマージ可否（`review-merge` / `autonomous`）

**全行に「必ず人間確認で停止する条件」（SKILL.md）が掛かる**（該当すれば `clean` でも自律マージしない）。

| 終了のしかた | マージ |
|---|---|
| `STATUS=clean` で本文にも P0 / P1 が無い | 可 |
| `STATUS=clean` だが本文に `[P2]` が残る | 可。**全件を修正（条件付き再レビュー適用）または accept 記録**してから |
| `STATUS=findings` で P0 / P1 が残る | 不可（解消必須。修正して再実行） |
| 記録系 docs だけの差分で Codex をスキップした | 可（下記「記録系 docs の Codex スキップ」の条件をすべて満たす場合） |
| `error` / `halt-tokenlimit` | 不可（原因を潰してから再実行。人間へ返してよい） |
| 残る指摘がすべて人間確定区分 | 不可（ユーザーの判断待ち） |

## 記録系 docs の Codex スキップ

差分が**記録系の許可リストに閉じている**PR は Codex を実行せず、自己レビュー（P0 / P1 なし）＋ CI 緑でマージしてよい。記録は次のレビューで指示として読まれる資産ではなく、Codex のラウンドを掛ける価値が低いため。

- **許可リスト（proj-poker。一次情報はここ。他文書は参照だけ）**: `docs/taskLog/**`（作業ログ）のみ。`docs/research/**`・`docs/decision_log.yaml`・番号付き正本 docs は記録系ではない（仕様・判断の正本）ため対象外
- **1 ファイルでも含めば対象外**（通常どおり Codex を回す）: `CLAUDE.md`・`AGENTS.md`・`README.md`・`.claude/**`・設計書（`docs/0*_*.md`・`docs/1*_*.md`・`docs/decision_log.yaml`・`docs/research/**`）・セットアップ手順・プロンプト定義・環境の現状記録・コード・設定
- **判定は機械的に**: `git diff --name-only <base>...HEAD`（base は PR の base ブランチ。stacked PR で `origin/main` を使うと親側の差分まで含めて誤判定する）の全行が許可リストの prefix に一致すること（目視で「記録だろう」と決めない）
- **記録義務**: PR コメントに `## 🤖 Codex レビュー結果` を残し、「記録系差分のため Codex をスキップ」と対象ファイル一覧・自己レビューの結果・CI の結果を書く
- 許可リストは prefix で機械判定するため、記録ファイルの中に手順・規範の変更が混ざっている場合は拾えない。**記録ファイルへ規範を書かない**（規範は設計書・skill へ）ことが前提で、混ざっていると気づいたらスキップせず通常経路で Codex を回す

## 学習 Capture の位置

レビューで受けた指摘を次の PR で受け直さないために、`review-learning` skill（Capture）を**次の 2 箇所で必ず呼ぶ**:

1. **各ラウンドの finding 処理を終えた時点**（修正 / accept / 非該当の記録が確定した時点。自己レビューの指摘でも Codex の指摘でも同じ）
2. **ループの出口**（`clean` / `findings` / `error` / `halt-tokenlimit` のどれで終わっても。Codex を実行できなかった回も対象）。未記録の候補が残っていればここで記録する

- Capture が書くのは **PR コメントと PR 本文だけ**。台帳（`code-review/references/learned-checks.md`）・`implementation-guidance`・memory は feature PR で書き換えない（`[P0]` / `[P1]` 由来でも同じ。急ぐなら `create-issue` で distillation の Issue を立てる）。
- 学習の確認をループの出口に固定するのは、マージできた回だけ振り返ると、人間確定待ち・上限到達で止まった PR —— 最も学ぶことが多い回 —— の知見が毎回捨てられるため。
- `REVIEW_LEARNING=blocked` はマージ可否に影響しない。distillation が未実施であることも元の PR のマージを止めない（別 Issue のライフサイクル）。
- 候補の変換（台帳・ガイダンスへの追記・昇格・棚卸し）は `review-distillation` skill が**独立した harness PR** で行う。発火条件（同じ root failure class が別 PR で 2 回・P0/P1 の高再利用・`issue-patrol` の巡回）はそちらが一次情報。

## 修正をプッシュした場合

修正プッシュ後は**必ず ClaudeCode 自己レビュー（Step 1）を改めて実施**し、PRコメントを追記する。Codex の再実行は「finding の処理」4 の**条件付き再レビュー**の表で決める（P0 / P1 の修正と①〜④に当たる修正は必須、それ以外の P2 だけの局所修正は不要）。

## `STATUS=clean` の信頼性（必ず本体確認）

`codex-review.sh` の終了出力に `STATUS=clean` と書かれていても、**コメント本体に P0/P1/P2 の findings が含まれていることがある**（誤判定）。長期レビュー反復の PR で、`STATUS=clean` 表示のままコメント本文に整合性・構造的問題の指摘が残ることがある。

必ず以下のいずれかで**最新コメント本体を直読**してから判断する:

```bash
# 推奨: --paginate で全ページ取得 + jq -s でスラープ
gh api --paginate repos/takumi-sano22/proj-poker/issues/<PR番号>/comments | jq -s 'add | last | .body'

# 代替: ページサイズを 100 に増やす（コメント数 < 100 ならこちらでも可）
gh api 'repos/takumi-sano22/proj-poker/issues/<PR番号>/comments?per_page=100' --jq '.[-1] | .body'
```

`STATUS=clean` を鵜呑みにしてマージすると、後の動作確認で「Codex 指摘していたとおりに動かない」事象に遭遇する。

> **やってはいけない記法**:
> - `gh api repos/.../comments --jq '.[-1] | .body'` — ページ 1（デフォルト 30 件）しか取らないので、コメント超過時に古い末尾を拾う
> - `gh api --paginate repos/.../comments --jq '.[-1] | .body'` — `--paginate` 付きでも `--jq` は**各ページに適用**されるので、複数ページ分の末尾が複数行出力される（最新を取れない）
>
> **`jq -s`（slurp）または `per_page=100`** を使って配列を 1 つに合体させてから `.[-1]` を適用するのが正解。長期レビュー反復 PR では特に必須。

## Codex sonnet フォールバックの扱い

Codex 本体がトークン制限に達すると `codex-review.sh` は Sonnet フォールバックで代替レビューを生成する（`REVIEWER=sonnet`）。「Sonnet フォールバックは無関係指摘で信頼不可」と**全否定せず内容で判断**する:

- **妥当な指摘の例**: hydration mismatch・CSS transition 不発火・モーダルの自己半透明化のような UX 矛盾・既存機能との競合リスク
- **過剰/文脈外の指摘の例**: 仕様の境界相談を「実装バグ」と扱う・既に自己レビューで残課題化済みの内容を再提起

判断軸:
- 実装バグ（React/CSS/SSR 仕様違反） → 修正必須
- UX 矛盾 → 妥当性高い（自己レビューで見落としやすい観点）
- WCAG/視認性などスペック相談 → 実装変更不要、実機確認かフォロー Issue 化
- 完全に文脈外 → 無視可

## Codex ループが長期反復になった場合の判断

`autonomous` モードで「3 回ルール」を超えても収束しないことがある。**3 回ルールは「同じ問題のループ」を防ぐためのもの**で、各回が**別々の妥当な指摘**であれば修正を続ける判断は妥当（上限を引き上げるのではなく、内容で続行を判断する）。**同じ形の指摘が 3 回以上続く**（別のコマンド・別の数値・別の経路で同じ境界が破られる）ときは、個別の修正を続けずに**判定の構造そのものを変える**（列挙 → 許可リスト、別の場所に持つ状態 → 対象自身に持たせる、等）。ただし以下のサインが出たら、ユーザー判断を仰ぐタイミング:

1. **指摘内容が構造的問題で shallow 修正不可** — 例: CSS 仕様レベルの制約など、設計案を複数試しても根本解決しないもの。その場合は `AskUserQuestion` で 3〜4 択を提示して方針確認する。
2. **同じ箇所に複数回指摘が来る（4 回目以降）** — サマリ整合性レベルのノイズ的指摘が増えてくる傾向。
3. **設計書・ADR・コメントの 3 箇所以上で記述ズレが連発** — 設計書の修正だけで実装が変わらない場合、grep で全箇所同期して 1 回でまとめて修正する。
4. **修正と Codex 指摘が「もぐら叩き」になる** — 別箇所を直すと別箇所が壊れる → ロールバックして設計から見直すか、ユーザー判断を仰ぐ。

> **要点**: 構造的制約で shallow に解決できないと判断したら、機械的に「Codex 指摘へ対応」を続けず、`AskUserQuestion` で方針を確認して不要な実装試行を打ち切る。**「Codex の指摘に対応するのが正しい」と機械的に進めない**判断が重要。
