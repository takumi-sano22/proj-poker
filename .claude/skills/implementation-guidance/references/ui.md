# ui — Table UI・フォーム・複数表示経路を書く前の判定基準

**本書が一次情報である範囲**: 実装時の確認動作。**一次情報が別にある範囲**: 画面要件・表示ルールは `docs/06_UI_UX.md`、デザインの実装値は `ui-design-recipes` skill、実額常時表示は D49（`docs/decision_log.yaml`）。3D は非採用。

## 書く前に決めること

> **レビュー時にも当たる欠陥クラスは台帳が一次情報**（LC-040 新しい面は全表示経路に配線・他画面への漏れ / LC-041 非同期 UI 状態の 2 層ガード / LC-042 file input の value リセット / LC-043 ストリームイベントの型と whitelist）。書く前に一読し、ここには繰り返さない。

1. **実額は常時表示し、BB 表示は補助にする**（D49）。Stack・Pot・Bet 額から実額を消して BB だけにしない。
2. **一時的な失敗の案内は驚かせない文言にし、再送ボタンへ誘導する**（ユーザーの操作で復旧できることを示す）。
3. **キーボード移動は入口が複数ある前提で書き、位置は出口で読む**。
4. **SSR hydration（SSR 採用時のみ）**: `Math.random()` / `Date.now()` を初期値に使わない（`code-review` F 節。山札の乱数は UI で生成しない）。
5. **Tailwind 採用時: クラスが効くかは dev サーバー無しで実測できる**（`@tailwindcss/node` → `setContent` → `getComputedStyle`。対照要素を並べる）。UI は Playwright で実機幅を実測する。
6. **Tailwind 採用時: ソース検出起点の外に画面コードを置くなら `@source` を足す**。
7. **共有フック（キーボード移動・フォーカス制御等）の挙動を変えるときは、着手前に呼び出し元を全部列挙し「キーの種類 × 要素の種類 × キャレット位置 × 修飾キー × IME」の挙動表を先に書く**。DOM 順と視覚順がズレる場所（`justify-between` の左右）は脱出先を属性で明示する。到達しにくい画面は、フックが動いている画面へ要素を注入して本物のハンドラで検証する。
8. **非同期に取得して表示する状態（提案・検索結果）は、実装前に「その状態がいつ古くなるか」の経路を全部列挙する**（主経路を通らない切替操作が盲点）。後から 1 つずつ塞ぐと巡回数が伸びる。
9. **注釈付き画面図の枠は「大きい図の中の要素を指す」ためのもの**。小さい図（ピル・トグル 1 個）には注釈を付けず図＋短い平文、見れば分かる図はタグのみ。文字を減らす作業では落ちた情報を一覧で確認する。
10. **デザイン体系が違う画面（例: 標準色直書きの画面と役割トークンの画面）のコンポーネントを相互にコピーしない**。

## 確認動作（実装後・自己レビュー前）

- 表示経路（例: Table 表示 / Review 表示、PC / モバイル）それぞれで該当の面を 1 回開く（Playwright のスクリーンショットでよい）
- 隣接する画面の見た目が変わっていないことを 1 画面で確認
- 連打・切替で古い応答が残らないことを確認
