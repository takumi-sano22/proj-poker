# llm — プロンプト・オーケストレーション・評価を書く前の判定基準

**本書が一次情報である範囲**: 実装時の確認動作。**一次情報が別にある範囲**: Model Role と出力検証は `docs/03_SYSTEM_ARCHITECTURE.md` §3 / §5、Opponent / Review の設計は `docs/05_AI_OPPONENTS_AND_REVIEW.md`、モデル名の未確定事項は `docs/11_OPEN_ITEMS.md` OI-001、品質改善の全プロセスは `llm-quality-improvement` skill。情報境界・出力検証の判定基準は `references/ai-boundary.md`。

## 書く前に決めること

> **レビュー時にも当たる欠陥クラスは台帳が一次情報**（LC-050 評価ハーネスと本番の引数組み立て経路の一致）。書く前に一読し、ここには繰り返さない。ハーネスを書くときは本番の引数の詰め直しまで grep し、出力のバイト一致を実測する。

1. **直接 SDK を呼ばない**。Claude API 呼び出しは 1 か所の抽象を経由し、モデル名は role-based config（`opponent_fast` / `review_standard` / `review_deep`・OI-001）で解決する。コードへ直書きしない。
2. **API キーはローカル Runtime 側だけが持つ**。UI（ブラウザ側）へ渡さず、リポジトリ・ログ・Event Log にも書かない。
3. **1 変更 1 測定**。測定中にプロンプトを触らない。効果が落ちたら意図ではなく**文字列で**前版と比較する。
4. **条件付き指示は守られない**: 「〜のときだけ〜する」はコード側の boolean で文ごと出し分ける（構造ゲート）。
5. **指示は触れただけで隣のケースを変える**: 例外を足したら隣接ケースも測る。節ごとに出し分ける。
6. **字数指示が出力の中身を決める**。長さの指定は意図した内容の優先順位と一緒に決める。
7. **横並び評価の集計スクリプトは入口ガードを最初から置く**: run 数が前提とちょうど一致（欠けた run を黙って除外しない）、各 run の行 ID が母集団と過不足なく一致、条件・モデル・期待値の版が同一。

## 確認動作（実装後・自己レビュー前）

- 変更したプロンプトを本番経路と同じ引数で 1 回実行し、ハーネスと同じ出力形が返ることを確認
- 測定を伴う変更は、ベースライン → 変更後を同条件で 3 回以上取り、集計の入口ガードを先に置く
- レート制限（429）で計測が壊れる API は、呼び出し間隔を空けて検証する
