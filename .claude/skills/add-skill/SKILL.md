# スキル追加・管理スキル

新しいスキルを追加・改善するためのスキル。指示書やワークフローをスキル形式に変換したり、ゼロから新しいスキルを作成する。

大まかなプロセスは以下のとおり：

- スキルが何をすべきか、どうやるかを決める
- SKILL.md のドラフトを書く
- テストプロンプトを作り、スキル付きのClaudeで実行する
- ユーザーと一緒に結果を定性的・定量的に評価する
- フィードバックに基づいてスキルを改善する
- 満足できるまで繰り返す

ユーザーがこのプロセスのどこにいるかを判断し、適切な段階から支援を開始すること。たとえば「Xのスキルを作りたい」なら最初から、すでにドラフトがあるなら評価・改善ループから始める。

## skill 品質チェックリスト（判定基準・一次情報）

このプロジェクトの skill が満たすべき品質基準を、**機械的に点検できる形**でここに一元化する。新規 skill 作成時の自己点検、および既存 skill の棚卸しの判定基準として、**本チェックリストを一次情報として参照する**。以下の各項目は、下の「SKILL.md のフォーマット」「スキル設計の原則」「スキルの構造」を要約したもので、詳細はそれぞれの節を見る。

| # | 項目 | 判定基準（外れたら要改修） |
|---|---|---|
| 1 | **命名** | ディレクトリ名と frontmatter `name` が **kebab-case** で一致している |
| 2 | **配置** | `.claude/skills/<skill-name>/SKILL.md` の **1箇所**に置かれている（本プロジェクトは単一配置。他ワークスペース由来の「2箇所配置」表現は適用しない）。global（`~/.claude/skills`）と同名で併存させてよいのは次の 2 型だけで、どちらも `.claude/README.md`「global / project 重複 skill の優先規則」（CLAUDE.md から移設した一覧）に載せる: ①**フォールバック型**（global に他プロジェクト用の汎用版がある。内容は異なってよく、project 版を優先する）②**同一内容型**（他プロジェクトでも使う汎用 skill を両方に同じ内容で置く。例: `ui-design-recipes`。project でだけ読む固有の補強は project 版にだけ置き、以後の変更は両方に当てる） |
| 3 | **description のトリガー充実** | ①何をする skill か、②トリガーキーワード、③具体的な発話例（「〜して」形式）を含む。アンダートリガー防止のため押しは強めでよい。**ただし description は全セッションで読み込まれるので短く保つ**（英語のトリガー語は任意。語や発話例を並べすぎない） |
| 4 | **本文行数** | **500行以内が目安**。超過するものは `references/` へ分離を検討（下記「例外」参照） |
| 5 | **WHY 説明** | 主要な指示に「なぜそうするか」の理由が添えられている。`ALWAYS`/`NEVER` の大文字連呼に頼っていない |
| 6 | **汎化** | 特定の1例だけで動く狭い指示になっていない（幅広いケースに対応する指針になっている） |
| 7 | **段階的開示** | 大きい補足は `references/` に分離し、SKILL.md 内で「いつ読むか」を明記。300行超の reference には目次がある |
| 8 | **重複がない** | 他 skill・`CLAUDE.md` と内容が重複していない（重複は一次情報を1箇所にして他方は参照にする） |

### 例外・運用ルール

- **KISS・依頼範囲外リファクタ禁止**。基準を外れる skill だけを最小改修し、問題のない skill は触らない。
- 行数・語数は**目安**であり、必要に応じて超えてよい（#4/#7）。数値だけで機械的に不合格にせず、可読性・段階的開示が保たれているかで判断する。

配置は `.claude/skills/<skill-name>/SKILL.md`（プロジェクト）または `~/.claude/skills/<skill-name>/SKILL.md`（global）。判定の一次情報は上の品質チェックリスト #2。

proj-poker の既存 skill は `.claude/skills/` 直下（`ls .claude/skills`）が一次情報。新規作成前に同名・類似 skill がないか確認する。ドメイン固有の skill（`poker-invariant-review` など）の作成予定は Issue #4。

## SKILL.md のフォーマット

```markdown
---
name: skill-name-here
description: "スキルの説明文。何をするスキルか＋どんなキーワードやリクエストでトリガーすべきかを明記する。トリガーキーワードは代表的なものに絞って含めること。"
---

# スキルのタイトル

（ここにスキルの本文を記述）
```

### フロントマターのルール

- **name**: kebab-case で記述（例: `weekly-report`）
- **description**: トリガー条件として機能する。以下を含めること：
  - スキルが何をするかの簡潔な説明
  - トリガーすべきキーワードの列挙（英語は任意。全セッションで読み込まれるので並べすぎない）
  - 具体的なユーザー発話例（「〜して」形式）

#### descriptionの書き方のコツ

Claudeはスキルを「使わなすぎる」傾向がある（アンダートリガー）。これを防ぐため、descriptionは「少し押しが強い」くらいがちょうどよい。

**悪い例:**
```
"週次レポートを作成するスキル。"
```

**良い例:**
```
"週次レポートを作成するスキル。ユーザーが週報、ウィークリーレポート、今週のまとめ、進捗報告、weekly report、活動報告などに言及したら必ずこのスキルを使用すること。「レポート書いて」「今週何やったかまとめて」「進捗を報告したい」といったリクエストでもトリガーする。"
```

descriptionにはスキルの用途だけでなく「いつ使うべきか」の文脈情報も含める。本文ではなくdescriptionがトリガーの主要メカニズムである。

**ただし、description は全セッションで常にコンテキストに載る。** 語や発話例は代表的なものに絞り、長さは 300 字前後までを目安にする（上の良い例は約 140 字）。英語のトリガー語は任意。細かな使い分けや話題の列挙は本文（または本文の対応表）に書く。

### 本文のルール

- 500行以内を目安にする（長くなる場合は `references/` にファイルを分離）
- 命令形で書く（「〜せよ」「〜すること」）
- 理由・背景も説明する（「なぜそうするか」があるとClaudeがより適切に判断できる）
- 具体的なコマンド例やテンプレートを含めると効果的

## スキル設計の原則

### 原則1: WHYを説明する

「何をすべきか」だけでなく「なぜそうするか」を説明する。今日のLLMは賢く、理論的な理解があれば指示を超えた適切な判断ができる。

**避けるべき書き方:**
```
ALWAYS use h2 headings for sections. NEVER use h3.
```

**推奨する書き方:**
```
セクション見出しにはh2を使う。h3だと目次生成時に階層が深くなりすぎ、
読者がドキュメント構造を把握しにくくなるため。
```

ALWAYS/NEVER を大文字で書きたくなったら黄色信号。理由を説明して、モデルが「なぜ重要か」を理解できるようにリフレームする方が、より効果的で柔軟なスキルになる。

### 原則2: 汎用的に書く

スキルは多くの異なるプロンプトで使われることを想定する。特定の例にだけ機能する狭い指示ではなく、幅広いケースに対応できる一般的な指針を書く。

### 原則3: プロンプトを簡潔に保つ

効果のない指示は削除する。テスト実行時のトランスクリプトを読み、スキルがモデルに無駄な作業をさせている部分がないか確認し、あれば該当部分を削除する。

## スキルの構造（Anatomy）

```
skill-name/
├── SKILL.md (必須)
│   ├── YAML フロントマター (name, description 必須)
│   └── Markdown 形式の指示本文
└── バンドルリソース (任意)
    ├── scripts/    - 決定的・反復的な処理の実行コード
    ├── references/ - 必要時にコンテキストに読み込むドキュメント
    └── assets/     - 出力に使うファイル（テンプレート、アイコン、フォント等）
```

### Progressive Disclosure（段階的開示）

スキルは3段階のロードシステムで動作する：

1. **メタデータ**（name + description）— 常にコンテキストに存在（約100語）
2. **SKILL.md 本文** — スキルがトリガーされたときにコンテキストに読み込まれる（500行以内が理想）
3. **バンドルリソース** — 必要なときだけ読み込み（サイズ制限なし、スクリプトはロードせずに実行可能）

これらの行数・語数は目安であり、必要に応じて超えてもよい。

### 主要パターン

- SKILL.md は500行以内に収める。超えそうな場合は階層を追加し、次にどこを読むべきか明確に記述する
- SKILL.md からリファレンスファイルへの参照は明確に書き、いつ読むべきかのガイダンスを添える
- 大きなリファレンスファイル（300行超）には目次を付ける

### ドメイン別構成

スキルが複数のドメインやフレームワークをサポートする場合、バリアントごとに整理する：

```
cloud-deploy/
├── SKILL.md (ワークフロー + 選択ロジック)
└── references/
    ├── aws.md
    ├── gcp.md
    └── azure.md
```

Claudeは関連するリファレンスファイルだけを読み込む。

## 本文の書き方パターン

### 出力フォーマットの定義

テンプレートを明示すると、Claudeが安定した出力を生成しやすくなる：

```markdown
## レポート構成
以下のテンプレートに従うこと：
# [タイトル]
## エグゼクティブサマリー
## 主要な発見
## 推奨事項
```

### Examples パターン

具体例を含めるとスキルの精度が上がる：

```markdown
## コミットメッセージのフォーマット
**例1:**
入力: ユーザー認証にJWTトークンを追加した
出力: feat(auth): JWT ベースの認証を実装

**例2:**
入力: ログインフローのバリデーションバグを修正した
出力: fix(auth): ログインバリデーションの不具合を修正
```

### 命令形での記述

指示は命令形で書く。「〜してください」ではなく「〜すること」「〜せよ」を使う。

## 新しいスキルを作成する手順

### ステップ1: 意図の把握（Capture Intent）

まずユーザーの意図を理解する。現在の会話にすでにワークフローが含まれている場合（「これをスキルにして」等）は、会話履歴から情報を抽出する — 使ったツール、ステップの順序、ユーザーが行った修正、観察された入出力フォーマット。不足があればユーザーに確認し、次に進む前に合意を得る。

以下を確認する：

1. このスキルでClaudeに何をさせたいか？
2. どんな言葉・状況でトリガーすべきか？
3. 期待する出力フォーマットは何か？
4. テストケースを設定すべきか？（客観的に検証可能な出力 — ファイル変換、データ抽出、コード生成 — はテストケースの恩恵が大きい。主観的な出力 — 文体、デザイン — は必要ないことが多い）

### ステップ2: ヒアリングとリサーチ

エッジケース、入出力フォーマット、サンプルファイル、成功基準、依存関係について積極的に質問する。テストプロンプトを書くのはこの段階が固まってからにする。

利用可能なMCP・ツールを確認し、リサーチに有用であれば活用する（ドキュメント検索、類似スキルの調査、ベストプラクティスの確認等）。ユーザーの負担を減らすため、事前にコンテキストを集めておく。

### ステップ3: SKILL.md を作成

ヒアリング結果をもとに SKILL.md を作成する。上記の「スキル設計の原則」と「本文の書き方パターン」に従うこと。

ドラフトを書いたら一度新鮮な目で読み返し、改善する。

### ステップ4: 配置

```bash
mkdir -p .claude/skills/<skill-name>/
# SKILL.md を .claude/skills/<skill-name>/ に配置

```

### ステップ5: 動作確認

配置後、次のセッションでスキル一覧に表示されることを確認する。
ユーザーにトリガーキーワードを伝え、試しに呼び出してもらう。

## テストと評価

### テストケースの作成

スキルのドラフトを書いたら、2〜3個の現実的なテストプロンプトを作成する。実際のユーザーが言いそうなリクエストにする。

ユーザーに共有する：「以下のテストケースを試したいと思います。これで良いですか？追加したいものはありますか？」

テストケースは `.claude/evals/evals.json` に保存する：

```json
{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "ユーザーのタスクプロンプト",
      "expected_output": "期待される結果の説明",
      "files": []
    }
  ]
}
```


### 評価とフィードバック

結果をユーザーに提示し、フィードバックを得る。定性的な評価（出力の質、意図との一致）と、可能であれば定量的な評価（正確性、フォーマット準拠）の両方を行う。

## スキルの改善ループ

テストケースを実行し、ユーザーがレビューしたら、フィードバックに基づいてスキルを改善する。

### 改善の考え方

1. **フィードバックから汎化する。** 数個の例で繰り返しイテレーションしているが、目的はあらゆるプロンプトで機能するスキルを作ること。その例だけで動くスキルは無意味。細かい調整やオーバーフィットではなく、異なるメタファーや作業パターンを試みる。

2. **プロンプトを簡潔に保つ。** 効果のない記述は削除する。テスト実行のトランスクリプトを読み、スキルがモデルに非生産的な作業をさせている部分を特定して除去する。

3. **WHYを説明する。** モデルに求める行動の背景にある理由を伝えることに注力する。LLMは賢く、理論的理解があれば指示を超えて適切に判断できる。ALWAYS/NEVER の大文字連呼よりも、「なぜ重要か」を説明する方がはるかに効果的。

4. **繰り返しパターンをスクリプト化する。** テスト実行で全ケースが同じヘルパースクリプトを書いていたら、そのスクリプトをスキルにバンドルすべきサイン。`scripts/` に一度書けば、将来の全実行が車輪の再発明をせずに済む。

## 既存の指示書をスキルに変換する手順

1. 指示書のmdファイルを読み込む
2. 内容を分析し、以下を抽出する：
   - 目的・ゴール
   - 実行手順
   - 使用ツール・コマンド
   - 出力フォーマット
   - 制約・注意事項
3. 適切な `name` と `description` を設計する（descriptionの書き方のコツを参照）
4. SKILL.md フォーマットに変換する（スキル設計の原則に従う）
5. `.claude/skills/<skill-name>/SKILL.md` に配置する

## 補足資料が必要な場合

スキル本文が長くなる場合（500行超）は、以下のように分離する：

```
skill-name/
├── SKILL.md          ← メインの指示（500行以内）
└── references/       ← 補足資料
    ├── detailed-guide.md
    └── templates.md
```

その他のバンドルリソース：

```
skill-name/
├── SKILL.md
├── scripts/          ← 決定的・反復的な処理のコード
│   └── generate_report.py
├── references/       ← 必要時に読み込むドキュメント
│   └── style-guide.md
└── assets/           ← テンプレート、アイコン等の出力用素材
    └── report-template.docx
```

SKILL.md の中で各リソースをいつ読む・使うべきかを明記すること。大きなリファレンスファイル（300行超）には目次を付けること。
