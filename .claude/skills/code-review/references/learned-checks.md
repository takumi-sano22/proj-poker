# learned-checks — レビューで学習したチェック項目（台帳）

`code-review` の**手順 1 で毎回読む**。過去のレビュー（第 2 段レビュー・自己レビュー・人間）で実際に指摘された内容を、出来事への参照を落として「**どういう条件のとき → 何を確認するか**」「**外すと何が起きるか**」へ変換したもの。差分を読む前に頭へ入れておかないと、前回と同じ見落とし方を再現する。

> **出典注記**: 初期項目（LC-001〜）は他PJ（Web アプリ）のレビューで実際に指摘された内容のうち、proj-poker にも通じる汎用教訓だけを残したもの（他PJ由来）。Prisma / GCP / Tenant / 認証固有の項目は削除済み。proj-poker 固有の項目は `review-distillation` skill が各領域の空き番号へ追記する（ポーカー不変条件は `poker-*` 領域を新設して 080〜 を割り当てる）。

## 運用規約（本ファイルが一次情報）

- **書き込むのは `review-distillation` skill だけ**（feature PR のレビュー中に思いついた観点をここへ直接足さない。候補は `review-learning` で PR コメントへ残す）。
- **対になる資産は `implementation-guidance`**（実装前に読む判定基準）。**同じ項目を両方へ置かない** —— 差分を見ないと判定できないものはここ、書く前に判定できるものはガイダンスへ。
- 1 行 1 項目。ID は `LC-NNN`。**領域ごとに 10 番台を確保**（共通 001〜 / db・persistence-event-log 020〜 / async 030〜 / ui 040〜 / llm 050〜 / docs・harness 070〜。010〜 と 060〜 は旧 api-auth・infra 用で欠番のまま再利用しない。ポーカー固有領域は 080〜 以降を割り当てる）し、領域内は追記順。10 番台を使い切ったら次の空き 10 番台をその領域へ割り当てる。欠番は詰めず、削除した ID は再利用しない。
- **再発**列: 別の PR で同じ項目が再び指摘されたら +1。**2 回以上で `code-review/SKILL.md` 本体へ昇格**し、この台帳からは削除する（判定は `review-distillation`）。
- **予算の目安**: `wc -m` で本体 SKILL.md + 本ファイル + 該当チェックリスト 1 本の合計 **20,000 字**。超えたら棚卸し（削除・圧縮・昇格）。機械検査は置かない。
- 領域は `code-review/SKILL.md`「差分クラス」の語彙と同じ（docs と harness は 1 つの節にまとめる。`persistence-event-log` は db 節、`ai-opponent` は llm 節に同居させてよい）。実装前ガイダンスは `.claude/skills/implementation-guidance/references/`（`docs` / `harness` は `docs-harness.md`）。差分がどのクラスかは同表で判定し、**該当セクションを重点的に、他は流し読み**でよい（コア = 「共通」は必ず読む）。

## db（SQLite・SQL・マイグレーション・Event Log 永続化）

| ID | 観点（条件 → 確認動作） | 外すと起きること | 再発 |
|---|---|---|---|
| LC-020 | **NULL 許容列を `WHERE` / `NOT IN` / `!=` / `<>` で使う SQL・ORM 条件で、NULL 行の扱いを明示しているか** —— 三値論理で NULL 行は比較結果が UNKNOWN になり、`NOT IN (…)` は 1 件でも NULL を含むと全件 false になる。`IS NULL` の分岐か `COALESCE` があるか | 除外したつもりの行が残る／含めたつもりの行が消える。件数が合わないまで気づかない | |
| LC-021 | **補償・ロールバック・クリーンアップ処理が行を削除していないか** —— 削除する場合、その行を前提にする再試行・再開・Replay が不可能にならないか。削除ではなく状態列の更新で表せないか（Event Log は追記のみが原則・D37） | 失敗時の補償が行を消し、同じ操作を再試行できなくなる／Replay が欠損する。復旧経路の欠陥はレビュー後半でしか見つからない | |
| LC-022 | **同一キーへ同時に到達しうる書き込み（枠取り・カウンタ・upsert）で、競合をどの機構で防いでいるか答えられるか** —— 一意制約／`SELECT … FOR UPDATE`／CAS（version 列）のどれか。「存在しないから INSERT」の判定は一意制約が要る（トランザクション分離の既定に依存しない。他PJ由来は PostgreSQL の READ COMMITTED） | 2 つの処理が同時に同じ枠を取り、上限を超える。テストは直列なので通る | |

## async（キュー・スケジューラ・バッチ・集約）

| ID | 観点（条件 → 確認動作） | 外すと起きること | 再発 |
|---|---|---|---|
| LC-030 | **キュー・ジョブ・再試行から呼ばれる処理が重複実行で二重の副作用を起こさないか** —— 冪等キーか一意制約で 2 回目を弾いているか。**CAS（version 比較）は時間差の再実行を弾けない**ので、処理済みマーカーが別に要る | 同じ Review 生成・同じ Projection 更新が 2 回走る。低頻度なので実運用でしか出ない | |
| LC-031 | **集約（Summary / Stats 等の Projection）の「上書き対策」と「削除対策」を別々に持っているか** —— 再計算で古い値を上書きしないガードと、元データ（Event）の訂正・削除時に集約から消すガードは別の経路で、片方だけ実装されがち | 削除したデータが日次集計に残る／再計算で新しい値が古い値に負ける | |
| LC-032 | **バッチ・Solver Subprocess・評価ジョブの完了判定を Monitor・ラッパーの通知だけで行っていないか** —— 「完了」と書く前に終了コード・出力ファイル・実データ件数（CI なら `gh run view --json status,conclusion`）で確認した記録があるか | Monitor が完了を誤検知し、実際は実行中・失敗のまま「完了」と報告する | |

## ui（Table UI・フォーム・複数表示経路）

| ID | 観点（条件 → 確認動作） | 外すと起きること | 再発 |
|---|---|---|---|
| LC-040 | **同じ機能が複数の表示経路（例: PC / モバイル、Table 表示 / Review 表示）を持つ画面へ新しい面（ボタン・モーダル・チップ）を足す差分で、全経路に配線され、片方の経路専用トークン（opacity・オーバーレイ等）が別画面へ漏れていないか** —— 共有コンポーネントの `className` 分岐を grep し、他の利用箇所で見た目が変わっていないか | 片方の経路だけ動かない／別画面の見た目が変わる。UI 修正 1 件のために後続 Issue が 1 サイクル増える | |
| LC-041 | **非同期に更新される UI 状態（読み込み中・提案・バッジ）に、requestId 等で古い応答を捨てるガードがあるか** —— `isLoading` の 1 層だけだと、遅れて届いた古い応答が新しい状態を上書きする | 連打・切替時に前の結果が表示される。再現が不安定でレビューで見つけにくい | |
| LC-042 | **`<input type="file">` を再利用する画面で、エラー後に `value` を空へ戻しているか** —— 同じファイルを選び直しても `change` が発火しない | 失敗後に同じファイルをもう一度選べず、ユーザーが操作不能に見える | |
| LC-043 | **ストリームや IPC・WebSocket のイベント type を足す差分で、受け側の型（union）とランタイム whitelist の両方に足しているか** —— 型だけ足すとイベントは黙って捨てられる。検証は受け側のパーサを実ソースから切り出して通す（サーバー直叩きでは見つからない） | 「サーバーは送っているのに UI が動かない」。fail-closed の分岐が一度も走らず、退行になる | |
